## 1. Summary

The product is a **compiler and consolidator**. Within an organization and a single event, operators add multiple client documents — uploaded files or, ideally, **live links** (Google Docs, Google Sheets, scripts, Airtable). The system compares them against each other and compiles them into a **playbook**: a real Google Sheet, created in the `studio@poweredbysage.com` Google Drive, following the styles and conventions of the SAGE playbook template. The playbook is what SAGE uses to run the event.

Two principles drive everything:

1. **Inconsistencies are expected and never block compilation.** Source documents *will* disagree. The compiler builds the playbook anyway and marks inconsistencies and unknowns in **red text** directly in the sheet. There is **no approval queue, no dropdown of changes/inconsistencies to approve** — the marks are a visual cue on the page itself, telling the humans running the event to ask for clarification.
2. **Sources are live.** When a client edits a linked document, the system notices and updates the playbook in (near) real time, marking **newly changed** values in **pink text**. Inconsistencies stay red.

## 2. What changes from v1

| Output | Internal "master" record, exportable as HTML | A real Google Sheet ("playbook") in `studio@poweredbysage.com` Drive, built from the SAGE template |

What stays: Organization → Event structure, the live-source sync loop (2-minute cron, revision-gated reads, immutable `sourceSnapshots`), Claude-powered extraction with the verbatim-snippet validator (sources remain **data**, embedded instructions are never followed), and full audit history.

## 3. Core flow

```
Org → Event → Sources (uploads + live links)
                 │  cron sync → immutable snapshots → diff
                 ▼
             Extraction (per source)
                 ▼
             Compiler (cross-source comparison)
                 ▼
             Playbook writer → Google Sheet in studio@poweredbysage Drive
                 ▼           (red = inconsistency/unknown · pink = new change)
             Split-screen UI (sources left / playbook right)
```

## 4. Ingestion

A source is anything a client gives us for the event:

- **Live links (preferred):** Google Docs, Google Sheets (exists today); **Airtable** links and shared scripts/documents (new connectors). Live sources are re-read when their revision changes; every read becomes an immutable snapshot.
- **File uploads (new):** PDF, Word, Excel, plain text, scripts. Stored in Convex file storage; each upload (or re-upload) becomes a snapshot like any other source.

All source types flow through the same snapshot → extraction → compile pipeline.

## 5. Compilation rules

1. **Always compile.** Missing or conflicting data never stops playbook generation.
2. **Inconsistency** = two or more sources disagree about the same field of the same entry, **or** a field the playbook needs has no value in any source ("unknown").
3. **Traceability stays.** Every compiled value must trace to a verbatim snippet in a source snapshot (existing validator in `lib/extraction.ts`). The compiler may *compare* across sources but never invents values.
4. **Cell value on conflict (proposed, open question §10):** show the value from the most recently updated source, in red; attach a Sheets **cell note** listing every candidate value and which source/revision it came from. The note is informational only — on the page, not an approval UI.

## 6. The playbook (Google Sheet)

- A real spreadsheet **created in the `studio@poweredbysage.com` Drive** via the existing dedicated Google connection, one playbook per event.
- Generated by **copying the SAGE empty-playbook template** (received: "Playbook Empty", file ID `1-ccUVXjoJXwTyZT4JQlMHrlHgS5aAgdsPWFSL9kQYMM`, stored as a template file ID in Settings) and filling it in. The compiler must respect the template's layout, styles, and conventions — it fills the template, it does not reinvent it. Full structure survey: [`TEMPLATE_CONVENTIONS.md`](TEMPLATE_CONVENTIONS.md).
- **Marking conventions — text color, not cell highlight/fill:**
  - **Red text** (`#CC0000` proposed): inconsistency between sources, or unknown/required-but-missing value. Persists until the sources agree or the value is confirmed.
  - **Pink text** (`#E91E8C` proposed): value changed because a client edited a source since the last compile. Stays pink while "new," then normalizes to black (decay rule: open question §10; proposed default — 24 h after the value last changed, configurable).
  - **Black text:** settled, consistent value.
  - Applied via Sheets API `textFormat.foregroundColor` (character/font color). No background fills, no highlights.
- **No approval surface anywhere.** The red/pink marks on the page *are* the interface: visual cues for the humans running the event to chase clarification with the client.
- Every write to the sheet is also recorded as a playbook revision in Convex (audit history survives even though approvals are gone).

## 7. Split-screen UI

Once a playbook exists, the event page becomes a split screen:

- **Right pane: the playbook** — the live Google Sheet, embedded.
- **Left pane: the sources** — every uploaded/linked document, with **browser-style tabs** across the top to switch between them. Tabs change only the left pane. Each tab renders the right viewer for its type (embedded Google Doc/Sheet, PDF viewer, text/script view, Airtable embed).
- **Adjustable divider:** the user drags the split left/right as needed.

## 8. Real-time behavior

- Existing cron reconciles live sources every 2 minutes (metadata probe; full read only on revision change). Target: a client edit is reflected in the playbook within one cycle.
- Pipeline on change: new snapshot → diff (`lib/snapshot-diff.ts`) → re-extract changed source → recompile affected entries → Sheets `batchUpdate` writing values + text colors.
- Changed values picked up this way are what turns **pink**.

## 9. Architecture mapping

**Keep:** `sources`, `sourceSnapshots`, sync cron (`convex/sync.ts`, `convex/crons.ts`), extraction (`lib/gateway-extraction.ts`, `lib/anthropic-extraction.ts`, validator in `lib/extraction.ts`), `lib/snapshot-diff.ts`, org/event/membership model, sealed Google token handling.

**Add:**
- `convex/playbooks.ts` + `playbooks` table: event → spreadsheet ID, template ID, per-cell map (entry/field → A1 range), per-cell mark state (`red` / `pink` / `none`) with timestamps.
- `lib/google-sheets-writer.ts`: copy template, map compiled entries into the template layout, `batchUpdate` values + `textFormat.foregroundColor`.
- Compiler step (cross-source comparison) replacing the proposal generator.
- File-upload sources (Convex file storage) and an Airtable connector.
- Split-screen event UI (tabs left, playbook right, draggable divider).

**Retire:** the pending-proposal approval flow and its UI (`masterProposals` pending/approve lifecycle, decision queue). `masterRevisions`-style auditing is retained as playbook revisions.

**Google scope change:** the dedicated account needs, in addition to read access to shared sources, permission to create and edit the sheets the app itself creates (`drive.file` + `spreadsheets`). Still one dedicated account, token still sealed server-side, clients still only ever *share* documents with it.
